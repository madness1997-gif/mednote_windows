# M4.1 native Note data foundation

M4.1 establishes a Windows-native persistence boundary for Note without
bringing React, IndexedDB, HTML editing, or the web editor's block JSON into
the runtime model.

## Content ownership decision

The hierarchy and document graph remain stable shared concepts:

- Workspace → Notebook → Section → Page → Sheet metadata;
- Document, Context, Group, NoteDocumentLink and DocumentLinkRelation;
- Library navigation preferences and active IDs.

Sheet content is platform-owned. Windows uses `RtfSheetContent` inside a
`NativeLibrarySnapshot` v1. The native runtime does not treat web v6
`SheetContent` JSON as its source of truth and does not keep a second editable
JSON copy beside the RTF document.

The exact web v6 DTO, validator and `json-safe-v1` backup codec live only under
`MedNote.Core.Compatibility.WebV6`. Required web fields and unknown extension
fields continue to round-trip inside that boundary.

## Windows record store

`MedNote.Infrastructure.FileNoteRepository` keeps hierarchy, document links,
preferences and RTF blob references in an atomically replaced
`manifest-v1.json`. Each Sheet body is a raw UTF-8 `.rtf` file in
`sheet-blobs`, addressed by its SHA-256 digest.

Loading hierarchy, document links or runtime preferences reads only the JSON
manifest. Opening a Sheet reads and validates exactly one RTF blob. A metadata
mutation reuses every existing blob.

A Sheet save writes and flushes an immutable RTF blob before replacing the
manifest. A crash before manifest replacement leaves at most an unreachable
blob; a crash after replacement leaves a complete snapshot. Later commits
collect unreachable blobs on a best-effort basis.

## Web v6 import boundary

Web import is a one-way compatibility workflow, not native persistence:

1. parse the `mednote-library-v2` envelope and require web schema v6;
2. validate shared hierarchy/document records and JSON Sheet ownership;
3. verify every marked `json-safe-v1` Sheet hash;
4. convert every web Sheet through `IWebV6SheetContentConverter`;
5. validate the complete native RTF snapshot;
6. write content-addressed RTF blobs and a staged manifest;
7. reload and compare the staged snapshot;
8. atomically replace the live manifest.

Conversion must finish before step 6. Any parse, hash, conversion, persistence,
or reload failure leaves the previous native Library current. M4.2 owns the
concrete RichEdit-based converter; M4.1 only defines and tests its boundary.

## Reader v1 cut-over

`ReaderV1Migration` maps Reader state, annotations, local PDF path, scroll
position and unknown fields into the shared Document graph of a native
snapshot. It never deletes or edits `reader-library-v1.json`. M4.2 will
activate the bridge only after the native snapshot has reloaded successfully.

## M4.1 non-goals

- no Reader/Note split shell or F6 routing;
- no RichEdit UI or concrete web→RTF converter;
- no rich-text toolbar or First Aid blocks;
- no source-anchor navigation;
- no RTF→web export and no shared editor-content runtime model;
- no deletion of Reader v1 persistence.
